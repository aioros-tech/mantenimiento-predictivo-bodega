AIOROS · Predictive maintenance for the tuna cold store · Code review

Deploying to the Jetson needed small changes; the review found an existing problem in the alert texts

Moving the system to the Jetson took two small changes to the existing code plus a new deployment module. None of them changes a single figure in the results. While reviewing the Jetson's real output we found a problem that already existed on the Mac: in most reports for units in alert, the text says the unit is normal. The status computed by the code is correct; the text is not. This review explains the changes, what we verified and seven findings by priority.

Why it was needed

The forecasting model was always downloaded from the internet under a name hard-coded in the source. On the Jetson it has to load from a local copy of one exact version, so it works offline and never changes on its own.

What changed

An environment variable, TFM_MODEL, can point at that local copy; by default it is still the same name as before. Writing moved into its own function, generate_text(), so the service loads the language model once instead of for every report. Also, when a model fails to load, the real reason is now shown instead of always blaming Gemma's licence.

  • Without the environment variable, behaviour is the same as before
  • redactar() returns the same as before; it only delegates to the new function
  • The new function writes every report the service produces on the Jetson
  • The full script, with the PDF, ran on the Jetson before this change and was not re-run afterwards

Main finding · predates the deployment

The alert texts say the unit is normal

We reviewed the 16 reports the Jetson produced in its first cycles. In 7 of them the forecast crosses the alarm limit and the status is ALERT. Only 1 of those 7 texts mentions the crossing; 5 say the unit is operating in its normal range or that there is no risk. The Mac produced the same text for the same case, so the problem does not come from the deployment.

Blast freezer 1 · cycle 2status: ALERT
El blast freezer 1 está funcionando dentro del rango normal con una lectura actual de 88.9 unidades del sensor. […] lo que indica que no hay riesgo inmediato de sobrecalentamiento o daño estructural.
"…operating within its normal range… which means there is no immediate risk…"
What the code computed: the forecast crosses the 89.3 limit in ≈ 2 minutes.
Blast freezer 1 · published dashboard (Mac)status: ALERT
Este comportamiento ascendente indica una tendencia positiva, aunque aún no supera el límite de alarma.
"…although it does not yet exceed the alarm limit."
What the code computed: the forecast crosses the limit in ≈ 8.5 minutes.
Cause

It is not only the language model. Stage 3, which is code, hands it the sentence "El equipo opera en rango normal" (the unit is operating in its normal range) whenever the current reading is below the limit, even when the forecast crosses it. The crossing warning comes further down the list, and the model tends to stick with the first sentence.

Why the guardrail misses it

The guardrail only checks numbers. "Normal range" and "no risk" contain no numbers, so they pass.

What limits the damage today

The ALERT status, the verdict and the dashboard table are computed by the code and are correct. The risk is someone reading only the text.

Recommended fix

1) Say "operating in its normal range" only when the forecast does not cross the limit, and put the warning first. 2) Add a meaning check to the guardrail: if the status is ALERT, the text must mention the crossing and must not say "normal range" or "no risk"; if it fails, show a text assembled by the code instead.
